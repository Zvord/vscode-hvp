# HVP Language Support

VS Code support for the HVP (Hierarchical Verification Plan) language used by Synopsys
Verification Planner.

This extension is a **thin LSP client**. All language intelligence (parsing, diagnostics,
completion, outline, folding) lives in the standalone `hvp-language-server` npm package
(sibling repo, `../hvp-language-server`); this repo only wires that server into VS Code
and ships a generated TextMate grammar for syntax highlighting. See `CLAUDE.md` in this
folder for the file-by-file map.

## Features

- Syntax highlighting for `.hvp` files (keywords, types, built-in metrics, strings,
  numeric/percent literals, comments) — `syntaxes/hvp.tmLanguage.json`, generated by
  `hvp-language-server`'s grammar generator (see "Syntax grammar" below).
- Feature outline: the Outline view and "Go to Symbol" (`Ctrl+Shift+O`) list every
  `feature` block, nested to match the file's actual `feature ... endfeature` hierarchy.
  Only features are shown — measures, metrics, plans, subplans, overrides, and filters are
  intentionally excluded.
- Block snippets: typing a block-opener keyword (`plan`, `feature`, `metric`, `measure`,
  `override`, `filter`, `until`) and accepting the suggestion inserts the full
  `<keyword> <name>; ... end<keyword>` skeleton with tabstops. Sent by the server as
  `insertTextFormat: Snippet` completion items — there's no local `snippets/hvp.json` file
  anymore.
- Autocompletion: block keywords, built-in attributes/annotations (`description`, `weight`,
  `owner`, `at_least`, `phase`, `source`, `test.expected`), built-in metric names (`Line`,
  `Group`, `test.*`, etc.), type keywords, and aggregator names — all offered everywhere, but
  ranked by what block the cursor is currently inside (e.g. `source` sorts first inside a
  `measure`, `measure`/`metric` sort first inside a `feature`). Suppressed inside strings and
  comments. Triggers automatically after `.` (for dotted names like `test.expected`).
- Auto-indentation: a line ending a `feature ...;` declaration increases the indent of the
  next line; `endfeature` decreases it (`language-configuration.json`, client-side).
- Block folding: every `plan`/`feature`/`metric`/`measure`/`override`/`filter`/`until` block
  can be folded, from the server's `foldingRangeProvider`.
- Problems (diagnostics), refreshed as you type (debounced 300ms server-side):
  - **Error** — a statement line doesn't end with a `;` (block closers like `endfeature`/
    `endmeasure`/`endmetric`/`endoverride`/`endfilter`/`endplan`/`enduntil` are exempt, and a
    line ending in `,` is treated as a continued list, e.g. a multi-line `source = "...", "...";`).
  - **Error** — block imbalance, treating every block pair (`plan`/`endplan`,
    `feature`/`endfeature`, `metric`/`endmetric`, `measure`/`endmeasure`,
    `override`/`endoverride`, `filter`/`endfilter`, `until`/`enduntil`) like matching
    parentheses: an unclosed block left open at end of file, a close keyword with no matching
    open, or a close keyword that doesn't match the innermost open block.
  - **Warning** — a `feature` block has no nested features and no measures.
  - **Warning** — a `measure` block has no `source` assignment.

## Known limitations (v1)

- Source-region keywords inside `source = "..."` strings (`module:`, `instance:`, `tree:`,
  `property:`, backtick wildcard/regex tags like `` `r` ``/`` `n` ``) are not tokenized —
  the whole string is highlighted as a plain string literal.

## Settings

- `hvp.server.path` (string, default empty) — path to a local `hvp-language-server`
  checkout's launcher script (e.g. `/path/to/hvp-language-server/bin/hvp-language-server.js`),
  for developing against a server build other than the one bundled into this extension.
  Leave empty to use the bundled server (see "Bundling" below). Requires a window reload
  after changing.
- `hvp.trace.server` (`"off"` | `"messages"` | `"verbose"`, default `"off"`) — logs the raw
  LSP request/response traffic between this extension and the server to the "HVP Language
  Server" output channel. Useful when diagnosing why a feature isn't behaving as expected
  server-side.

## Setup

```
npm install
npm run compile
```

`hvp-language-server` is currently installed as a `file:../hvp-language-server` path
dependency (it hasn't been published to npm yet), so **the sibling `hvp-language-server`
repo must exist, checked out next to this one, and already built** (`npm run compile`
there) before `npm install` here will succeed.

`npm run compile` runs `tsc -p ./` (type-checking only) and then `node esbuild.js`, which
bundles `src/extension.ts` and a self-contained copy of the `hvp-language-server` dependency
into `out/extension.js` and `out/server.js` respectively (see "Bundling" below). Use
`npm run watch` to recompile `.ts` on save for type-checking during development — it does
**not** re-run the esbuild bundle step, so re-run `npm run compile` (or `F5`, which does this
for you via the `npm: compile` task) to pick up code changes in the actual running extension.

## How the LSP connection works

`src/extension.ts` (~40 lines) constructs a `vscode-languageclient` `LanguageClient` with:
- `documentSelector: [{ language: 'hvp' }]` — only activates for `.hvp` files.
- `ServerOptions` pointing at the server entry point (`out/server.js` by default, or
  `hvp.server.path` if set) with `transport: TransportKind.stdio` — the server
  (`createConnection(ProposedFeatures.all)` in `hvp-language-server/src/server.ts`) reads
  `process.argv` itself and switches to stdio transport when it sees the `--stdio` flag,
  which `vscode-languageclient` appends automatically for this transport kind.

VS Code spawns the server as a separate Node child process per workspace; all the actual
diagnostics/completion/outline/folding logic runs there, not in the extension host process.

## Running the extension

1. Open this `vscode-hvp` folder as the workspace root in VS Code.
2. Press `F5` (or Run > Start Debugging). This uses the `Run Extension` launch
   configuration in `.vscode/launch.json`, which:
   - runs the `npm: compile` build task first (`.vscode/tasks.json`), so you don't need to
     compile manually beforehand,
   - launches a second VS Code window — the **Extension Development Host** — with this
     extension loaded.
3. In that new window, open a `.hvp` file, e.g.
   `../hvp-language-server/test/fixtures/realistic-sample.hvp` (relative to this repo's
   parent folder), to see syntax highlighting, diagnostics, completion, outline, and folding.
   The extension is only active inside this dev host window, not your main VS Code window,
   unless you've separately installed a packaged build (see Packaging below).

If you'd rather not use `F5`, run `npm run compile` manually and launch the dev host from a
terminal instead (adjust the path to wherever you've checked this repo out):
```
code --extensionDevelopmentPath=/path/to/hvp/vscode-hvp /path/to/hvp/hvp-language-server/test/fixtures/realistic-sample.hvp
```

### Pointing at a local server checkout during development

By default the extension runs the server bundle produced at build time
(`out/server.js`, from whatever `hvp-language-server` version is in `node_modules`). To
iterate on the server itself without re-running this extension's `npm install`/build each
time:

1. In `../hvp-language-server`, run `npm run compile` (or `npm run watch`) after each change.
2. In the Extension Development Host window, set `hvp.server.path` (Settings UI or
   `settings.json`) to the absolute path of
   `../hvp-language-server/bin/hvp-language-server.js`.
3. Reload the dev host window (`Ctrl+R` / `Cmd+R`, or "Developer: Reload Window") to restart
   the client against that path instead of the bundled server.

## Debugging

- The client side (`src/extension.ts`) is small — set breakpoints there before `F5` and use
  the main VS Code window's Debug Console/variables pane as normal. Source maps are enabled
  (`tsconfig.json` → `sourceMap: true`, and `esbuild.js` also emits `.map` files), so
  breakpoints in the `.ts` file bind correctly even though VS Code runs the bundled
  `out/extension.js`.
- The actual analysis logic (diagnostics, completion, outline, folding) runs inside the
  server's child process, not the extension host — debugging that means attaching to the
  server process directly, or (usually simpler) working against
  `hvp-language-server`'s own test suite (`npm test` there) and its
  `test/serverSmoke.test.ts`, which drives the compiled server over real `--stdio` without
  needing VS Code at all. See `hvp-language-server/CLAUDE.md`.
- Set `hvp.trace.server` to `"verbose"` and check the "HVP Language Server" output channel
  (Output panel, dropdown in the top-right) to see the raw LSP messages flowing in both
  directions — the fastest way to tell whether a bug is client-side (VS Code UI/wiring) or
  server-side (the actual language logic).
- To inspect exactly which TextMate grammar scope was assigned to a token (useful when
  highlighting looks wrong), use "Developer: Inspect Editor Tokens and Scopes" from the
  Command Palette in the dev host window, then click a token.
- The Outline view's tree can be checked directly against the file: e.g.
  `grep -n "^\s*feature\|^\s*endfeature" some.hvp` shows every open/close pair, which should
  match the nesting shown in the Outline 1:1.

## Syntax grammar

`syntaxes/hvp.tmLanguage.json` is a **generated file** (see its own `"//"` header comment) —
it is `hvp-language-server`'s `generated/hvp.tmLanguage.json`, checked into this repo as-is.
It is NOT hand-edited here. To pick up a keyword change made in
`hvp-language-server/src/core/keywords.ts`:

```
cd ../hvp-language-server
npm run gen-grammars
cp generated/hvp.tmLanguage.json ../vscode-hvp/syntaxes/hvp.tmLanguage.json
```

(`hvp-language-server`'s own `generated/` folder is gitignored there, since it's fully
derived — this repo's copy under `syntaxes/` is the one actually checked into git.)

## Bundling

`npm run compile` bundles both the client and a self-contained copy of the server into
`out/` via `esbuild.js`, so that `out/extension.js` and `out/server.js` don't need
`node_modules` present at runtime — this is what makes the packaged `.vsix` (which excludes
`node_modules` via `.vscodeignore`) actually work standalone. Both `hvp.server.path`
(pointing outside `out/`) and the default in-package server continue to work identically
either way, since the client only ever sees a file path to launch.

## Packaging (.vsix)

```
make
```

This is `make package` (the default target): it runs `npm run compile` first, then packages
whatever just got built into `hvp-<version>.vsix` in this folder. Files listed in
`.vscodeignore` (`src/`, `.vscode/`, `tsconfig.json`, `node_modules/`, etc.) are excluded
from the package — safe now that `npm run compile` bundles everything the extension needs
into `out/` (see "Bundling" above). `make clean` removes `out/` and any `.vsix` files.

Equivalent manual steps, if you'd rather not use `make`:
```
npm run compile
npx --yes @vscode/vsce@2.15.0 package
```

**Node version note:** on Node 18, the latest `@vscode/vsce` (and even `@vscode/vsce@2`
unpinned) pull in a transitive `undici` dependency that expects a global `File` class only
available from Node 20+, and fails with `ReferenceError: File is not defined`. Two things
fix it:
1. Pin `@vscode/vsce@2.15.0` (as above) instead of an unpinned/latest version.
2. If that alone still fails, polyfill the missing global before running vsce — keep the
   polyfill file **outside** this folder so it doesn't get bundled into the `.vsix`:
   ```
   echo "if (typeof globalThis.File === 'undefined') { globalThis.File = require('node:buffer').File; }" > /tmp/file-polyfill.cjs
   NODE_OPTIONS="--require /tmp/file-polyfill.cjs" npx --yes @vscode/vsce@2.15.0 package
   rm /tmp/file-polyfill.cjs
   ```

If you're on Node 20+, plain `npx @vscode/vsce package` (no pin, no polyfill) should work
directly.

### Installing the packaged .vsix

- In VS Code: Extensions panel → `...` menu → "Install from VSIX..." → select the
  `hvp-<version>.vsix` file.
- Or from a shell with the real `code` CLI on PATH:
  ```
  code --install-extension hvp-<version>.vsix
  ```

### Before publishing further

This repo is licensed under MIT (see [`LICENSE`](./LICENSE)), and `package.json` has
`license`/`author`/`repository`/`bugs`/`homepage` filled in with real values. Two things
are still placeholders:

- `package.json`: `"publisher": "local"` is only a placeholder too — it's fine for local
  packaging/installs as done above, but publishing to the VS Code Marketplace (a separate
  step from just open-sourcing on GitHub) requires registering a real publisher id via
  `vsce create-publisher` / `vsce login` and putting that id here instead.
- `dependencies.hvp-language-server` is a `file:../hvp-language-server` path dependency,
  which only works when this repo is checked out next to `hvp-language-server` — swap it to
  a real version range (`"^0.1.0"`) once `npm publish` actually runs for
  `hvp-language-server` (see `../hvp-language-server/README.md`'s "Publishing" section).
  Also relevant for packaging: `npm install` with a `file:` dependency copies (or symlinks,
  npm-version-dependent) the sibling repo's `files` allowlist into `node_modules` at install
  time, not at `vsce package` time — re-run `npm install` after changing
  `hvp-language-server` if `npm run compile`'s bundle step seems to be using stale server
  code.
